# Improvement Changelog

Real sequence, not reconstructed after the fact. Evidence values are real numbers or real
test/run output, not estimates. See `docs/evaluation-results.md` for the full evaluation table.

| Stage | What you tried and why | Evidence | Decision / learning |
|---|---|---|---|
| Baseline | A single LLM call given the student profile and target role, asked directly to recommend what to learn and build. | 0.25 average skill-gap-to-project coverage across 10 profiles; 0 out of 5 named gaps on 3 profiles. | Established the starting point. A single unstructured prompt doesn't reliably tie its own recommendation back to a specific named skill, which is why the substring-match scorer found nothing to credit on those 3 cases. |
| Iteration 1 | Built the six-agent LangGraph pipeline (Profiler, Industry Analyst, Skill Mapper, Gap Analyst, Project Architect, Validator) with a bounded Validator-to-Architect revision loop, instead of one bigger prompt. | Two passing tests (`tests/test_graph.py`) proving the loop actually revises: a deliberately incomplete mission on pass one gets caught and a second, complete mission is produced on pass two. | Kept. The revision loop is what separates this from six chained LLM calls; without it there's no verification step at all. |
| Iteration 2 | Noticed the Skill Mapper called the LLM once per unmapped concept, roughly 15-20 calls for a single plan. Added a static taxonomy for the industry-side vocabulary, a batched single call for whatever's left, and an on-disk cache keyed by (role, concept). | Calls dropped to 0-1 per run in the common case (`tests/test_skill_mapper.py` asserts exactly one call for a batch of unmapped concepts, and zero on a repeat run). | Kept. Never call an LLM once per item in a loop; batch it, cache the result, since the translation is deterministic. |
| Iteration 3 | Added Groq as a second provider (OpenAI-compatible endpoint) so the pipeline doesn't require a paid Anthropic key to run. Hit two real provider-specific failures immediately: the assumed model name didn't exist on the account, and the model actually available (`openai/gpt-oss-120b`) spends hidden reasoning tokens that silently ate a tight `max_tokens` budget, returning Groq's `json_validate_failed` with no output. | Confirmed via `client.models.list()` for the first, and via a live 400 error with an empty `failed_generation` field for the second. Fixed with a real model lookup and a retry loop that escalates `max_tokens` specifically on that error code. | Kept. A model name and a token budget are both provider-specific facts, not portable constants; verify them against the live account rather than assuming they carry over from another provider. |
| Iteration 4 | Real user test with an actual student profile (3 real GitHub projects) returned "0% on every required skill," despite the student clearly being a working Python/ML practitioner. Traced it to the Skill Mapper translating skills into free-form industry phrasing ("Computer Vision" -> "computer vision / real-time inference") that could never exactly equal a job posting's literal skill name, so real evidence could never suppress a gap. | Before: Python and Docker both at 0% for a profile with explicit "built in Python... deployed with Docker" project text. After: same input, Python and Docker at 60% (medium-confidence evidence correctly counted), with only the genuinely uncovered gaps (Model monitoring, CI/CD, Cloud deployment, Kubernetes) remaining. | Kept. Constrained the Skill Mapper to a closed set: it may only map onto one of the target role's actual literal skill names, or skip the concept. This is the single highest-impact correctness fix in the project; see the hot take. |
| Iteration 5 | Added transparency and follow-up actions the first version was missing: surfaced GitHub-fetch failures instead of silently degrading, surfaced real job-posting frequency per gap (previously computed and discarded), added a baseline-comparison button, and wired the Phase 2 work simulation (sprint-by-sprint submission against the real Sprint Manager agent) into the UI. | Manual verification: a profile with unreachable GitHub URLs now shows an explicit warning banner instead of a silently thinner result; sprint submission returns real pass/fail/partial feedback from a live call. | Kept. All four were things the pipeline already computed or could already do; none of them needed new agent logic, only surfacing what existed. |
| Iteration 6 | Added a live streaming trace (`/generate-plan/stream`, one NDJSON line per agent) and an animated "generating" screen. First version auto-redirected to results the instant the stream finished. | User feedback: it "disappears instantly," no time to read the trace. | Revised, not removed: kept the stream, replaced the auto-redirect with a button that only enables once the plan is ready, so the reader controls the pace. |
| Iteration 7 (removed) | First visual redesign pass: dark background, rounded cards with shadows, an orange/emerald accent pair, Fraunces/Manrope fonts, gradient-blob backgrounds. | User feedback: "looks like every other AI slop website... now looks Claude generated." | Removed entirely. The specific tell wasn't quality, it was genericness: dark mode plus a warm-accent-on-slate palette plus heavily rounded shadowed cards is a recognizable template shape regardless of how carefully it's executed. Learning: "professional and elegant" defaults toward a narrow, over-represented visual pattern; avoiding it takes an active, different reference point, not just more polish on the same one. |
| Final | Rebuilt the visual design around a light paper background, an oxblood/gold accent pair (deliberately outside orange, purple, blue, green), Newsreader/IBM Plex Sans/IBM Plex Mono, flat hairline-bordered sections instead of shadowed cards, and numbered sections echoing the project's own six-agent pipeline diagram. Ran the full 10-profile evaluation for real. | All 4 app routes render clean, `tsc`/`next build` pass, 7/7 backend tests pass. Real evaluation: 0.25 baseline vs 0.68 agent average coverage. | Main contribution: the closed-set Skill Mapper fix (Iteration 4) is what makes the 0.68 number honest rather than inflated by phantom matches; the six-agent architecture with a real revision loop is what makes 0.68 achievable at all. |
